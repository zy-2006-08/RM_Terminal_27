DEFECTS FOUND AND FIXED IN THIS PASS
  All four were found by reading the code and the harness against the actual
  binaries BEFORE the first full run, not by watching it fail.
  1. Log contradicted exit status. `aboutToQuit` logged a hard-coded exit=0
     while a failed capture returned 5, so the evidence package could contain a
     record that disagreed with the process result. The handler now logs the
     code actually returned. Both paths verified: success logs exit=0, and a
     capture into an unwritable directory returns 5 and logs exit=5.
  2. Harness would have crashed. The malformed payload "\x00\x01\x02broken" was
     passed as an argv string; Python rejects embedded NUL bytes with
     ValueError, which would have aborted the whole run. Binary payloads now go
     through stdin via `mosquitto_pub -s`.
  3. Reconnect check was a false pass. It waited for the substring "MQTT
     subscribed (readonly)", which the FIRST subscribe already wrote, so the
     check passed without any reconnect happening. It now requires a second
     occurrence.
  4. Read-only proof was vacuous. The scenario never started the simulator, so
     "no control publish observed" passed against a 0-byte wire. It now runs the
     simulator and asserts the terminal consumed telemetry while being watched.
  Also fixed: two runs wrote to the same gui-stdout.log, so the mqtt-down run
  overwrote the normal run's evidence; and the inbound-family check used a
  substring test against binary protobuf payloads, which could match by
  accident. Topic matching is now anchored at line start.

WHY THE HARNESS WAITS 11 SECONDS IN THE NORMAL SCENARIO
  sim/match_server.py returns stage 1 then stage 3 for the first 10 seconds of
  elapsed time, and `tick_10hz` returns early outside stage 4, so `Event` is
  effectively unpublishable before then. Without the wait, the 6/6 family
  assertion fails for a timing reason rather than a defect. This is a property
  of the simulator's match schedule, not of the terminal.
