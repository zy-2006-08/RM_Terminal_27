DECODED_FRAMES UNDER LOSS IS AT THE THEORETICAL CEILING, NOT A DEFECT
  Measured in decode-ceiling.log:
    asset: access_units=372, irap_keyframes=0, access_units_with_parameter_sets=12
    clean full decode = 360 frames
    correct reassembly semantics (whole access units only):
      2% loss  -> ceiling 15/27/42 frames (seeds 11/12/13)
      10% loss -> ceiling 1 frame (all seeds)
  The receiver measured 12 frames at 2% and 0 at 10%, i.e. at that ceiling.
  Reason: correct reassembly emits only COMPLETE access units, so one lost
  fragment removes a whole reference frame, and the asset contains no IRAP
  keyframe to re-sync from. Byte-level truncation decodes 286/94 frames only
  because it feeds FFmpeg partial NALs it can error-conceal; a correct
  reassembler never produces that input. This is an asset/protocol property.

DEFECTS FOUND AND FIXED IN THIS PASS
  1. primeAccessUnit() appended to a single growing parameter_sets_ buffer, so
     every keyframe added another VPS/SPS/PPS copy without bound and each
     respawned decoder was fed dozens of duplicates. Now stores latest
     vps_/sps_/pps_ separately.
  2. Liveness used last completed FRAME. Under loss many access units never
     complete, so a healthy decoder was destroyed and the reassembly session
     reset. Liveness now follows datagram arrival (last_datagram_).
  3. The stall watchdog cleared only on a whole decoded frame and fired at 2s,
     killing a decoder that was buffering legitimately. It now clears on ANY
     decoder output, waits 5s, and additionally requires the decoder to be
     genuinely mute (no new stderr) before recovering.
  4. A respawned decoder is re-primed from cached parameter sets instead of
     waiting for one of the 12 in-band parameter-set access units.
